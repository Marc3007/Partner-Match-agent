# Architecture

This document covers two things the project brief asks for that go beyond
the MVP in this repo: the proposed Postgres + pgvector schema for migrating
off `lib/vendors.ts`, and the design of the separate scheduled enrichment
agent. Neither is implemented yet — the MVP intentionally ships with the
local dataset and matching engine described in the root `README.md` so the
product experience could be validated first.

## Current state vs. target state

| Concern | MVP (this repo) | Target |
|---|---|---|
| Vendor data | `lib/vendors.ts`, static, in the app bundle | Postgres, `vendors` + related tables below |
| Semantic match | **Real Claude classification (implemented, see below) when `ANTHROPIC_API_KEY` is set; local keyword/phrase overlap as an honestly-disclosed fallback otherwise** | `pgvector` embedding similarity over `problem_tags` for very high query volume, if per-query Claude calls become a cost/latency bottleneck |
| Enrichment | Automated bootstrap (done, see below) + a recurring Claude Code Routine (implemented, see below) | Standalone scheduled worker service per the cadence table in the brief, with a confidence-scored review queue and its own Postgres-backed credentials |
| Feedback | In-memory (`app/api/feedback/route.ts`) | `feedback_events` table, replayable into a training set |
| Field history | Not tracked | `field_history` table, append-only |

The matching service and the enrichment worker stay two separate deployables
(per the brief's non-functional requirements): the enrichment worker only
ever writes to staging/review tables, and the matching API only ever reads
from the "live" columns.

## Proposed schema

```sql
-- Enums -------------------------------------------------------------

create type vendor_tier as enum ('core_validated', 'consulting_backed', 'standard');
create type vendor_ecosystem as enum
  ('Microsoft', 'AWS', 'Google', 'SAP', 'Salesforce', 'Oracle', 'IBM', 'Adobe', 'independent');
create type complexity_level as enum ('low', 'medium', 'high');
create type company_size as enum ('startup', 'mid_market', 'enterprise');
create type review_status as enum ('pending', 'approved', 'rejected');
create type proof_type as enum ('case_study', 'press_release', 'active_engagement');

-- Core reference data -------------------------------------------------

create table categories (
  id            smallserial primary key,
  name          text not null unique
);

create table vendors (
  id                    uuid primary key default gen_random_uuid(),
  legacy_id             text unique,             -- keeps the v001..v200 ids from partner-database.json
  name                  text not null,
  category_id           smallint not null references categories(id),
  tier                  vendor_tier not null default 'standard',
  vendor_ecosystem      vendor_ecosystem not null default 'independent',
  -- Self-referencing FK for corporate parent/umbrella grouping (e.g. every
  -- Salesforce Cloud points here to the "Salesforce" row). NULL means this
  -- row IS the flagship/parent itself. The app's effective parent is
  -- `coalesce(parent_company_id, id)` -- see lib/types.ts's `parentCompany`
  -- for why this exists: two products of the same company must never be
  -- shown as independent "different vendors" in a single recommendation
  -- (top-3 selection, the stack builder, and alternatives all dedup on it).
  parent_company_id     uuid references vendors(id),
  implementation_complexity complexity_level,
  typical_duration_weeks_min smallint,
  typical_duration_weeks_max smallint,
  existing_stack_synergy_note text,
  created_at            timestamptz not null default now(),
  updated_at            timestamptz not null default now()
);

create index on vendors (parent_company_id);

create table company_size_fit (
  vendor_id   uuid not null references vendors(id) on delete cascade,
  size        company_size not null,
  primary key (vendor_id, size)
);

-- Problem-tag taxonomy + matching --------------------------------------

create table problem_tags (
  id          smallserial primary key,
  slug        text not null unique,              -- e.g. 'customer-service-automation'
  label       text not null,
  tag_group   text not null                        -- e.g. 'Customer Experience & Support'
);

create table vendor_problem_tags (
  vendor_id     uuid not null references vendors(id) on delete cascade,
  problem_tag_id smallint not null references problem_tags(id),
  weight        real not null default 1.0,          -- lets a vendor be a stronger fit for tag A than tag B
  primary key (vendor_id, problem_tag_id)
);

-- pgvector embedding of a normalized description of what the vendor solves;
-- generated by the enrichment agent / a Claude classification pass, used to
-- replace the MVP's local keyword-overlap proxy without changing the shape
-- of MatchFactorBreakdown.semanticMatch in the API response.
create extension if not exists vector;

create table vendor_embeddings (
  vendor_id   uuid primary key references vendors(id) on delete cascade,
  embedding   vector(1536) not null,
  model       text not null,
  generated_at timestamptz not null default now()
);

create index on vendor_embeddings using ivfflat (embedding vector_cosine_ops);

-- Integration graph, for "Recommended stack" ---------------------------

create table vendor_integrations (
  vendor_id           uuid not null references vendors(id) on delete cascade,
  integrates_with_id  uuid not null references vendors(id) on delete cascade,
  source_url          text,
  last_verified        date,
  primary key (vendor_id, integrates_with_id)
);

-- Consulting-alliance validation (matching-adjacent, but never scored) --

create table consulting_validation (
  vendor_id     uuid primary key references vendors(id) on delete cascade,
  accenture     boolean not null default false,
  deloitte      boolean not null default false,
  pwc           boolean not null default false,
  bain          boolean not null default false,
  signal_count  smallint generated always as (
    accenture::int + deloitte::int + pwc::int + bain::int
  ) stored
);

create table delivery_partners (
  id            bigserial primary key,
  vendor_id     uuid not null references vendors(id) on delete cascade,
  partner_name  text not null,
  proof_type    proof_type not null,
  note          text not null,
  source_url    text,
  last_verified date,
  confidence_score real check (confidence_score between 0 and 1)
);

-- Context-only enrichment fields (never scoring inputs) -----------------

create table market_share_snapshots (
  id              bigserial primary key,
  vendor_id       uuid not null references vendors(id) on delete cascade,
  value_pct       real,
  scope           text,                 -- e.g. 'Global CCaaS market'
  source_url      text,
  source_name     text,
  year            smallint,
  confidence_score real check (confidence_score between 0 and 1),
  is_current      boolean not null default true,
  recorded_at     timestamptz not null default now()
);

create table review_scores (
  vendor_id     uuid primary key references vendors(id) on delete cascade,
  g2_score      real check (g2_score between 0 and 5),
  g2_review_count integer,
  source_url    text,
  last_verified date
);

create table case_studies (
  id            bigserial primary key,
  vendor_id     uuid not null references vendors(id) on delete cascade,
  title         text not null,
  industry      text,
  summary       text not null,          -- self-written summary only, per the brief -- never copied source text
  source_url    text not null,
  published_at  date,
  confidence_score real check (confidence_score between 0 and 1)
);

-- Versioning / audit trail -----------------------------------------------

-- One generic append-only table covers every enrichment field described in
-- the brief ("jedes Enrichment-Feld traegt last_verified, source_url,
-- confidence_score; alte Werte wandern in version_history"), instead of a
-- bespoke history table per field.
create table field_history (
  id              bigserial primary key,
  entity_table    text not null,        -- e.g. 'market_share_snapshots'
  entity_id       text not null,        -- fk value as text, since the target varies
  field_name      text not null,
  old_value       jsonb,
  new_value       jsonb,
  source_url      text,
  confidence_score real check (confidence_score between 0 and 1),
  changed_by      text not null,        -- 'enrichment_agent' | 'manual_review' | user id
  changed_at      timestamptz not null default now()
);

create index on field_history (entity_table, entity_id, field_name, changed_at desc);

-- Enrichment pipeline: staging + review queue ----------------------------

create table enrichment_candidates (
  id              bigserial primary key,
  vendor_id       uuid references vendors(id),
  target_table    text not null,        -- which table this candidate would update
  payload         jsonb not null,       -- proposed new field values
  source_url      text not null,
  confidence_score real not null check (confidence_score between 0 and 1),
  status          review_status not null default 'pending',
  reviewed_by     text,
  reviewed_at     timestamptz,
  created_at      timestamptz not null default now()
);

-- Product feedback loop ---------------------------------------------------

create table feedback_events (
  id            bigserial primary key,
  vendor_id     uuid not null references vendors(id),
  helpful       boolean not null,
  problem_text  text not null,
  company_size  company_size,
  complexity_tolerance complexity_level,
  existing_stack vendor_ecosystem[],
  created_at    timestamptz not null default now()
);
```

### Notes on the design

- **Nothing that feeds `field_history` or `enrichment_candidates` writes
  directly to a live table.** High-confidence, routine updates (a new case
  study from a vendor's own newsroom) can auto-promote from
  `enrichment_candidates` into the live table plus a `field_history` row in
  one transaction; anything unusual (a market-share jump, a tier change)
  stays `pending` for one-click review, per the brief's routing rule.
- **`vendor_embeddings` is additive**, not a replacement for
  `vendor_problem_tags`. Tags stay the explainable, editable layer shown in
  the UI's factor breakdown; the embedding is what the matching query
  actually ranks on once this migrates off the MVP's local keyword-overlap
  proxy. `MatchFactorBreakdown.semanticMatch` in `lib/types.ts` does not need
  to change shape when this happens.
- **Staleness badges** (brief section 5) are a read-time computation, not a
  stored flag: compare `field_history.changed_at` (or the relevant
  snapshot's `recorded_at`/`last_verified`) against that field's update
  cadence from the brief's table, and render the "Last checked: <date>"
  badge when it's overdue.
- **`legacy_id`** on `vendors` exists purely to keep `partner-database.json`'s
  `v001`..`v200` ids stable through the migration; drop it once nothing
  references those ids anymore.

## Enrichment automation: what's actually running today

Two things are implemented right now, and it's important to be precise
about what each one is (and isn't), since "automated enrichment agent" can
mean very different things:

**1. Bootstrap research (one-time, done).** 8 parallel Claude agents, each
given a 25-vendor batch, the full tag taxonomy, and instructions to
WebSearch each vendor's real public capabilities and translate them into
plain-language customer-problem tags. This populated `problemTags`,
`implementationComplexity`, `companySizeFit`, `integrationEcosystem`,
`sourceUrl`, and `confidenceScore` for 199 of the 200 original vendors (see
`README.md`'s Dataset scope section for the two flagged exceptions). The
script that merged the results into `lib/vendors.ts` is
`scratchpad/gen_vendors.py`, driven by
`scratchpad/parse_enrichment.py` output -- kept outside the repo since it's
a one-time migration tool, not part of the running app.

**2. Recurring enrichment Routine (implemented, Claude-Code-native).** A
scheduled trigger (Claude Code's own "Routine" primitive — a cron-style
wakeup, not a standalone service) fires periodically into a Claude Code
session with write access to this repo. On each firing it:
- reads `data/gap-reports.jsonl` (the persisted backlog written by
  `POST /api/gap-report` — see that route for why this is a file and not
  yet a database) for problems that repeatedly found no good category
  match, and treats those as candidate taxonomy/vendor gaps;
- re-researches vendors whose `lastVerified` is stale or whose
  `confidenceScore` was flagged low (currently just v200/Uptake) using the
  same WebSearch-grounded method as the bootstrap;
- regenerates `lib/vendors.ts` via `gen_vendors.py`, runs
  `npm run test:matching` and `npx tsc --noEmit`, and commits/pushes only if
  both pass.

This Routine is live: `trig_019cxqpWB5RgRRYLUwxfwaNG`, weekly (Mondays
03:00 UTC), spawning a fresh Claude Code session each run rather than
resuming a persistent one, so it's resilient to any single session ending.
Note it currently carries no MCP connector grants, so a fired run has git,
WebSearch, and normal file tools but not, e.g., GitHub-API MCP tools --
which is fine, since the job only needs to read/write files in this repo
and push over git.

**This is honestly a different thing from the brief's original design.**
The brief specifies a standalone deployable service with its own database
credentials, running independently of any chat session, on the cadence
table below (weekly/monthly/quarterly/semiannual per field type). What's
implemented here instead depends on Claude Code's own scheduling
infrastructure and a session that can reach this repository — it will not
run if that infrastructure is unavailable, and it is not a separately
deployable artifact the way the brief describes. It genuinely does remove
the "someone has to remember to run this" failure mode the brief is
worried about, but it is not a drop-in replacement for the Postgres-backed
worker below; that remains the target for a production deployment that
needs to run independently of Claude Code.

## Enrichment agent (scheduled worker) -- target design, not yet built

A separate deployable from the matching API, per the brief's non-functional
requirement of API-first / white-label-ready separation:

```
fetch (vendor newsroom / press search / job-postings API / analyst summary)
  -> extract candidate facts
  -> dedupe/diff against the live table
  -> confidence score (source-quality based)
  -> route:
       high confidence + routine change  -> auto-promote (writes live table + field_history)
       unusual/risky change              -> enrichment_candidates, status='pending'
```

Cadence follows the brief's table directly (weekly for case studies,
job-postings demand signal, and consultancy proof; monthly for market
share/analyst numbers; quarterly for consulting-alliance status; semiannual
for the category taxonomy) — implemented as one scheduled job per cadence
bucket rather than one giant nightly job, so a slow source doesn't block a
fast one.

## Real semantic matching (implemented)

**What was here before was not semantic matching, and calling it that was a
mistake worth naming plainly.** Through several rounds of fixes, `lib/matching.ts`'s
`semanticMatch()` was word-presence / bag-of-words matching against a
hand-maintained synonym list (`lib/tags.ts`'s `concepts: string[][]`): every
"fix" (recognizing "headless" vs. "headless commerce," "callcenter" vs.
"call center," "agile"/"strong" as non-category words) was a one-off patch
to that literal matcher, not an improvement to actual language
understanding. That pattern cannot converge — natural language has
unbounded surface variation, and no synonym list will ever enumerate all of
it. It also meant "coverage gap" detection was just a stopword list, unable
to distinguish a genuinely uncovered capability from an ordinary noun.

**`lib/semanticClassifier.ts` replaces this with a real Claude API call,
once per query:**

1. `classifyProblemTags(problem)` sends the user's free text plus the full
   ~102-tag taxonomy (id + label only, not vendor data — see the file's own
   comment for why classifying against the taxonomy is sufficient) to
   Claude (Haiku 4.5 by default, a bounded classification task rather than
   open-ended reasoning), asking for a relevance score per tag judged by
   *meaning*, not word overlap, plus a short list of any specific,
   substantive capability the taxonomy has no tag for at all.
2. `lib/matching.ts`'s `semanticMatch()`/`scoreVendor()` use that per-tag
   score map directly in place of the old `tagOverlap()` bag-of-words
   computation. Everything downstream is unchanged: the 0.55/0.20/0.15/0.10
   weighting, the relevance floor, the alternatives/stack logic, and the
   `MatchFactorBreakdown` shape the UI renders.
3. `runMatch()`'s `coverageGap` uses the classifier's own judgment of what's
   missing from the taxonomy when the LLM path ran, instead of the old
   stopword heuristic (which flagged "clients" and "persons" as gaps simply
   for not being 4+ character words on a fixed stoplist).
4. **Honest, disclosed fallback:** if `ANTHROPIC_API_KEY` is not set, or the
   API call fails or times out (15s), `classifyProblemTags` returns `null`
   and `runMatch` falls back to the local token matcher -- but `MatchResponse.matchingMode`
   (`'llm-semantic'` | `'keyword-fallback'`) tells the caller which one
   actually ran, and `ResultsView.tsx` renders a different, honest banner
   for each. The fallback is never silently presented as equivalent to real
   semantic matching.

**Cost/latency tradeoff, stated plainly:** this is one Claude API call per
query (not per vendor), taking a few seconds. For the volumes this MVP
handles that's a fine tradeoff for real understanding over pattern-matching;
if query volume grows enough that per-query latency/cost becomes a
constraint, the natural next step is precomputing embeddings for the fixed
tag taxonomy once and embedding only the incoming query per request (a
`pgvector` cosine-similarity lookup, no LLM call in the request path) --
`lib/semanticClassifier.ts`'s `classifyProblemTags()` function signature is
the seam to swap without touching `lib/matching.ts` again.
